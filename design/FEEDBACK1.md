# Handoff: `bcr_staging` Qt `6.10.2` Build & Rule Changes Needed for Downstream Consumers

This document summarizes the changes that were required—or uncovered as friction points—in the `bcr_staging` Qt `6.10.2` modules (`qt`, `qtbase`, `qtdeclarative`, etc., generated by `asymingt/qt_bazel`) when migrating the ROS Central Registry (49 direct Qt packages + Gazebo GUI/Tools + 24 indirect consumers) to link against Qt `6.10.2` shared libraries (`*_shared`).

---

## 1. Required Fix in `qtbase@6.10.2`: Stop Exporting Third-Party Static Libraries from `libcore_shared.so`

### Problem
In [`bcr_staging/modules/qtbase/6.10.2/overlay/BUILD.bazel`](file:///usr/local/google/home/simmers/development/ros-central-registry/bcr_staging/modules/qtbase/6.10.2/overlay/BUILD.bazel#L1301-L1306), the `qt_internal_library(name = "core")` target included `@rules_cc//cc/runfiles:runfiles` and `@zlib//zlib-1.3.2:z` in its `exports_filter`:

```python
    exports_filter = [
        "@qtbase//:__subpackages__",
        "@double-conversion//:__subpackages__",
        "@pcre2//:__subpackages__",
        "@rules_cc//cc/runfiles:runfiles",
        "@zlib//zlib-1.3.2:z",
    ],
```

In Bazel's `cc_shared_library` semantics, adding a target to `exports_filter` claims **exclusive ownership** of that static library across the entire dynamic dependency graph of any downstream binary. If any other `cc_shared_library` in the same binary's dependency graph also exports `@rules_cc//cc/runfiles:runfiles` (e.g. `librclcpp.so` in ROS 2) or `@zlib//:zlib` (e.g. `@rosdistro//cc:zlib`), Bazel fails at analysis time with:

```text
Two shared libraries in dependencies export the same symbols.
First shared library: @@qtbase+//:core_shared
Second shared library: @@rclcpp+//:rclcpp
Same exported target: @@rules_cc+//cc/runfiles:runfiles
```

### Fix Applied in `bcr_staging`
Remove `"@rules_cc//cc/runfiles:runfiles"` and `"@zlib//zlib-1.3.2:z"` from `exports_filter` on `core` in [`bcr_staging/modules/qtbase/6.10.2/overlay/BUILD.bazel`](file:///usr/local/google/home/simmers/development/ros-central-registry/bcr_staging/modules/qtbase/6.10.2/overlay/BUILD.bazel#L1301-L1306):

```diff
     exports_filter = [
         "@qtbase//:__subpackages__",
         "@double-conversion//:__subpackages__",
         "@pcre2//:__subpackages__",
-        "@rules_cc//cc/runfiles:runfiles",
-        "@zlib//zlib-1.3.2:z",
     ],
```

> [!IMPORTANT]
> When those two targets are not in `exports_filter`, `libcore_shared.so` still links them internally, which means `@zlib` and `@rules_cc//cc/runfiles:runfiles` must carry `tags = ["LINKABLE_MORE_THAN_ONCE"]` (already provided via the root module's `single_version_override` patches in [`tools/ci/patches/`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches)). Alternatively, `qtbase` could link against shared `cc_shared_library` wrappers for `zlib` in `dynamic_deps`.

## 2. Required Fix in `qt@6.10.2` (`qt.bzl`): Propagate `testonly` to Generated Helper Targets

### Problem
In `@qt//:qt.bzl` (`asymingt/qt_bazel`), the user-facing macros `qt_cc_library`, `qt_cc_binary`, and `qt_cc_test` synthesize intermediate helper targets before delegating to the final `cc_library` / `cc_binary` / `cc_test`:
- `<name>_moc` (`qt_moc`)
- `<name>_moc_lib` (`cc_library`)
- `<name>_hdrs_lib` (`cc_library`)
- `<name>_compile_srcs` (`qt_compile_ split`)

Previously, `qt.bzl` did not forward `testonly = True` to these intermediate targets. Whenever a `qt_cc_test` (or a `qt_cc_library(..., testonly = True)`) depended on a `testonly = True` target (such as `@googletest//:gtest` or a test helper library), Bazel rejected the build with:

```text
ERROR: non-test target '<name>_hdrs_lib' depends on testonly target '//test:mock_helper'
```

### Fix (Currently Applied via [`tools/ci/patches/qt/testonly_helpers.patch`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches/qt/testonly_helpers.patch))
Upstream this directly into `asymingt/qt_bazel`'s `qt.bzl`:
1. In `qt_cc_test`, always pass `testonly = True` to `<name>_moc`, `<name>_moc_lib`, `<name>_hdrs_lib`, and `<name>_compile_srcs`.
2. In `qt_cc_library` and `qt_cc_binary`, extract `testonly = kwargs.get("testonly", False)` and forward `testonly = testonly` to all generated helper targets (`_moc`, `_moc_lib`, `_hdrs_lib`, `_compile_srcs`, `_uic`, `_rcc`).

## 3. Recommended Improvements in `qt@6.10.2` (`qt.bzl`) for Downstream Ergonomics & LGPL Compliance

### 3a. Wrap `@qtbase` / `@qtsvg` / `@qtdeclarative` Labels in `Label(...)` Inside `qt.bzl`
Currently, `qt.bzl` injects raw string labels such as `"@qtbase//:core_shared"`, `"@qtbase//:offscreen"`, `"@qtbase//:xcb"`, `"@qtbase//:uic"`, `"@qtbase//:rcc"`, `"@qtsvg//:qsvg"`, and `"@qtdeclarative//:qml_plugins"` inside macro bodies.

Because raw strings in Starlark macros are resolved in the **caller module's** repository scope rather than `@qt`'s repository scope:
- Any downstream module calling `qt_cc_library`, `qt_cc_binary`, `qt_resource`, or `qt_ui_library` is forced to declare `bazel_dep(name = "qtbase")`, `bazel_dep(name = "qtsvg")`, and `bazel_dep(name = "qtdeclarative")` in its own `MODULE.bazel`, even if it only uses `qtWidgets`!
- **Recommendation**: Wrap all internal default labels in `qt.bzl` with `Label("@qtbase//:...")` so they resolve through `@qt`'s own `MODULE.bazel` dependencies.

### 3b. Do Not Inject `QT_BUILDING_QT` into `qt_cc_library` for Downstream Consumers
Currently, `qt_cc_library` in `qt.bzl` adds `"QT_BUILDING_QT"` to `local_defines`:
```python
local_defines = kwargs.pop("local_defines", []) + ["QT_BUILDING_QT"]
```
`QT_BUILDING_QT` is an internal Qt build macro intended only when compiling Qt itself (`qt_internal_library`). Defining it in downstream user libraries alters how Qt headers expand macros—most notably `Q_DECLARE_LOGGING_CATEGORY` / `Q_LOGGING_CATEGORY` in Qt 6.9+, causing internal linkage mismatches when consumer code defines logging categories across headers and `.cpp` files.
- **Recommendation**: Keep `"QT_BUILDING_QT"` in `qt_internal_library`, and remove it from the public `qt_cc_library` macro.

### 3c. Provide a Shared-Library-Aware Macro or Default `dynamic_deps` Helper for LGPL Consumers
To satisfy LGPLv3 dynamic linking requirements with `cc_shared_library`, every downstream shared library (`cc_shared_library`) and executable (`cc_binary` / `qt_cc_binary` / `qt_cc_test`) that links against `@qtbase//:core`, `@qtbase//:gui`, `@qtbase//:widgets`, etc. must **also** list the corresponding `*_shared` targets (`@qtbase//:core_shared`, `@qtbase//:gui_shared`, `@qtbase//:widgets_shared`, etc.) in `dynamic_deps`:
- If a consumer creates a `cc_shared_library` with `deps = [":my_qt_lib"]` (where `:my_qt_lib` depends on `@qtbase//:widgets`) and forgets to pass `dynamic_deps = ["@qtbase//:core_shared", "@qtbase//:gui_shared", "@qtbase//:widgets_shared"]`, Bazel silently links the static `libcore.a`, `libgui.a`, and `libwidgets.a` archives directly into the consumer's `.so`!
- Even worse, if a downstream `qt_cc_binary` then links that consumer `.so` alongside `qt_cc_binary`'s own automatic `@qtbase//:core_shared` `dynamic_deps`, Bazel fails with:
  ```text
  Do not place libraries which are alreadyExports in dynamic_deps or static_deps
  ```
  or violates LGPL by embedding static Qt into the intermediate `.so`.
- **Recommendation**:
  1. Either provide a `qt_cc_shared_library` macro in `@qt//:qt.bzl` that automatically populates `dynamic_deps` with the matching `@qt*//:*_shared` targets (just as `qt_cc_binary` and `qt_cc_test` already do), **or**
  2. Export a Starlark helper/list (e.g. `QT_SHARED_LIBS`) or provider so downstream rules can automatically collect `CcSharedLibraryInfo` from Qt dependencies without maintaining a manual `static -> _shared` mapping table.

## 4. Transitive BCR Static Libraries Requiring `LINKABLE_MORE_THAN_ONCE`

Because Qt's shared libraries (`@qtbase//:core_shared`, `@qtbase//:gui_shared`, `@qtbase//:xcb_qpa_shared`, `@qtmultimedia//:multimedia_shared`, etc.) statically link several foundational BCR C libraries without exporting them in `exports_filter`, any workspace that **also** builds other `cc_shared_library` targets using those same BCR libraries (such as OpenCV, OGRE, FreeType, libpng, X11, or `rclcpp`) triggers Bazel's `_build_link_once_static_libs_map` error unless those BCR libraries have `tags = ["LINKABLE_MORE_THAN_ONCE"]` (which compiles them with `-fPIC` and permits multiple `cc_shared_library` targets to link them internally).

In RCR, we currently apply the following root-module patches via `single_version_override` in [`tools/ci/setup_workspace.py`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/setup_workspace.py):
- [`tools/ci/patches/rules_cc/runfiles_linkable_more_than_once.patch`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches/rules_cc/runfiles_linkable_more_than_once.patch) (`@rules_cc//cc/runfiles:runfiles`)
- [`tools/ci/patches/zlib/linkable_more_than_once.patch`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches/zlib/linkable_more_than_once.patch) (`@zlib//:zlib`)
- [`tools/ci/patches/libpng/linkable_more_than_once.patch`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches/libpng/linkable_more_than_once.patch) (`@libpng//:libpng`)
- [`tools/ci/patches/freetype/linkable_more_than_once.patch`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches/freetype/linkable_more_than_once.patch) (`@freetype//:freetype`)
- [`tools/ci/patches/libx11/linkable_more_than_once.patch`](file:///usr/local/google/home/simmers/development/ros-central-registry/tools/ci/patches/libx11/linkable_more_than_once.patch) (`@libx11//:x11`, `@libx11//:x11_xcb`)

## 5. OpenGL (`@qtbase//:opengl`, `@qtbase//:openglwidgets`, XCB GLX/EGL, and `libGL` Stubs)

There are three distinct OpenGL issues across `@qtbase` on Linux that affect `gz-gui` (`MinimalScene` / `EngineToQtInterface`), `rviz_rendering`, `rviz_common`, `rviz_default_plugins`, and `octovis`:

### 5a. No XCB OpenGL Integration (`xcb_glx` or `xcb_egl`) Built on Linux
In [`bcr_staging/modules/qtbase/6.10.2/overlay/qtbase_config.bzl`](file:///usr/local/google/home/simmers/development/ros-central-registry/bcr_staging/modules/qtbase/6.10.2/overlay/qtbase_config.bzl#L501-L686), **all** X11/XCB OpenGL backends are disabled on Linux:
- `QT_FEATURE_xcb_glx_plugin` is `-1` (line 501)
- `QT_FEATURE_xcb_glx` is `-1` (line 646)
- `QT_FEATURE_xcb_egl_plugin` is `-1` (line 647)
- `QT_FEATURE_egl_x11` is `-1` (line 686)
- `QT_EGL_NO_X11` is `1` (line 506)

Correspondingly, [`bcr_staging/modules/qtbase/6.10.2/overlay/BUILD.bazel`](file:///usr/local/google/home/simmers/development/ros-central-registry/bcr_staging/modules/qtbase/6.10.2/overlay/BUILD.bazel#L4347-L4532) compiles `src/plugins/platforms/xcb/gl_integrations/qxcbglintegrationfactory.cpp` into `xcb_qpa`, but **never builds either XCB GL integration plugin**:
- `src/plugins/platforms/xcb/gl_integrations/xcb_glx/*` (`QXcbGlxIntegrationPlugin`) is not built.
- `src/plugins/platforms/xcb/gl_integrations/xcb_egl/*` (`QXcbEglIntegrationPlugin`) is not built.

**Impact**: On Linux under X11 (`QT_QPA_PLATFORM=xcb`), `QXcbIntegration::createPlatformOpenGLContext()` has no GL integration plugin to load and returns `nullptr`. Any application creating a `QOpenGLContext`, `QOpenGLWidget`, or QtQuick OpenGL scene graph (`rviz2`, `gz-gui`'s `MinimalScene` / `EngineToQtInterface`) will fail to acquire an OpenGL context on X11 at runtime.

**What the `qt_bazel` pipeline needs to do**:
- Enable `QT_FEATURE_xcb_glx_plugin = 1` / `QT_FEATURE_xcb_glx = 1` (and/or `QT_FEATURE_xcb_egl_plugin = 1` / `QT_FEATURE_egl_x11 = 1` without `QT_EGL_NO_X11`) in `qtbase_config.bzl`.
- Add `qt_static_plugin` targets in `qtbase/6.10.2/overlay/BUILD.bazel` for `qxcb-glx-integration` (`src/plugins/platforms/xcb/gl_integrations/xcb_glx/*.cpp`, requiring `@libxcb` GLX and `GL/glx.h`) and `qxcb-egl-integration` (`src/plugins/platforms/xcb/gl_integrations/xcb_egl/*.cpp`), and wire them into `@qtbase//:xcb` (and `_QTBASE_SHARED_MAP` in `qt.bzl`) so X11 apps automatically link the GLX/EGL integration plugins alongside `:xcb`.

### 5b. Incomplete `libGL` / `libGLX` Stubs in `gen_qopengl_gl1_stubs_cpp`
Because the hermetic LLVM sysroot on Linux does not ship `libGL.so` or `libEGL.so`, [`qtbase_config.bzl`](file:///usr/local/google/home/simmers/development/ros-central-registry/bcr_staging/modules/qtbase/6.10.2/overlay/qtbase_config.bzl#L1238-L1591) generates `gen_qopengl_gl1_stubs_cpp` and compiles it into `libgui_shared.so`. However:
1. It only stubs **14 OpenGL 1.x functions** (`glMatrixMode`, `glLoadIdentity`, `glOrtho`, `glLoadMatrixf`, `glGetString`, `glGetIntegerv`, `glFlush`, `glFinish`, `glViewport`, `glBindTexture`, `glTexParameteri`, `glTexParameterf`, `glTexImage2D`, `glTexSubImage2D`) and **zero `glX*` functions**.
2. Unlike macOS (`-framework OpenGL`) and Windows (`-lopengl32`), `@qtbase//:gui`, `@qtbase//:opengl`, and `@qtbase//:openglwidgets` have **empty `linkopts` on Linux**.
3. Downstream libraries that call standard OpenGL 1.1+ or GLX functions directly—such as `rviz_rendering` (`glXGetCurrentContext`, `glXGetCurrentDisplay`, `glXGetProcAddress`, `glXCreateContextAttribsARB`) or `octovis` (`glBegin`, `glEnd`, `glVertex3f`, `glClear`, `glEnable`, `glDisable`, `glDepthFunc`, `glBlendFunc`, `glReadPixels`, etc.)—fail to link under `lld` unless every consuming binary passes `-Wl,--allow-shlib-undefined`.
4. Even with `-Wl,--allow-shlib-undefined`, `gen_qopengl_gl1_stubs_cpp` opens `libGL.so.1` with `dlopen("libGL.so.1", RTLD_LAZY | RTLD_LOCAL)`. Because `RTLD_LOCAL` does not place `libGL.so.1` symbols into the global dynamic symbol table, unresolved `gl*`/`glX*` references in downstream `.so` files will fail at runtime unless `libGL.so.1` is either linked as a `DT_NEEDED` stub `.so` (`libGL.so.1` / `libGLX.so.0` / `libOpenGL.so.0` via `libglvnd` stub libraries) or opened with `RTLD_GLOBAL`.

**What the `qt_bazel` pipeline needs to do**:
- Provide a proper `libglvnd` / `libGL.so.1` + `libGLX.so.0` + `libEGL.so.1` stub shared library (or expand the exported GL/GLX stub table to cover the full OpenGL 1.x/GLX 1.4 ABI and use `RTLD_LAZY | RTLD_GLOBAL`), and link `@qtbase//:gui_shared` and `@qtbase//:opengl_shared` against it on Linux.

### 5c. Separation of `@qtbase//:opengl` and `@qtbase//:openglwidgets` from `@qtbase//:widgets`
In `rules_qt`, `@rules_qt//:qt_widgets` was an umbrella target that bundled `QtOpenGL` and `QtOpenGLWidgets`. In `qtbase@6.10.2`:
- `@qtbase//:opengl` (`libopengl_shared.so`) and `@qtbase//:openglwidgets` (`libopenglwidgets_shared.so`) are separate targets from `@qtbase//:widgets` (`libwidgets_shared.so`).
- Any package using `QOpenGLWidget`, `QOpenGLFunctions`, `QOpenGLExtraFunctions`, `QOpenGLShaderProgram`, `QOpenGLTexture`, or `QOpenGLBuffer` (`gz-gui`, `rviz_rendering`, `rviz_common`, `rviz_default_plugins`, `octovis`, etc.) must explicitly depend on `@qtbase//:opengl` and `@qtbase//:openglwidgets` in `deps`, and `@qtbase//:opengl_shared` and `@qtbase//:openglwidgets_shared` in `dynamic_deps`.
- Note also that in `qtbase/6.10.2/overlay/BUILD.bazel` (line 3800), `qt_internal_library(name = "openglwidgets")` sets `dynamic_deps = [":core_shared", ":dbus_shared", ":gui_shared", ":opengl_shared", ":widgets_shared"]` (via `_QTBASE_SHARED_MAP`), which is properly wired in `qt.bzl`.

## 6. Missing QML Static Plugin Targets & Disabled `QtNetwork` Features

### 6a. Missing QML Static Plugin Targets for Gazebo (`gz-gui`)
When migrating `bcr_staging/modules/gz-gui/10.0.0/overlay/BUILD.bazel` from `rules_qt` to `qt@6.10.2`, the following QML plugin targets existed in `@qtdeclarative` and were wired up:
- `@qtdeclarative//:qtquick2plugin`
- `@qtdeclarative//:quickwindow`
- `@qtdeclarative//:qtquickcontrols2plugin`
- `@qtdeclarative//:qtquickcontrols2basicstyleplugin`
- `@qtdeclarative//:qtquicklayoutsplugin`
- `@qtdeclarative//:qtquicktemplates2plugin`
- `@qtdeclarative//:qmlmodelsplugin`
- `@qtdeclarative//:qml_plugins`

However, `gz-gui`'s QML files also import several QML modules that are **not yet exposed** as `qt_static_plugin` / QML plugin targets in the `bcr_staging` overlays for `qtdeclarative`, `qtcharts`, and `qt5compat`:
1. `QtQuick.Controls.Material` (`qtquickcontrols2materialstyleplugin` in `qtdeclarative`)
2. `QtQuick.Dialogs` (`qtquickdialogsplugin` / `qtquickdialogs2quickimplplugin` in `qtdeclarative`)
3. `Qt.labs.platform` (`qtlabsplatformplugin` in `qtdeclarative`)
4. `Qt.labs.settings` / `QtCore` QML (`qtqmlcoreplugin` in `qtdeclarative`)
5. `QtCharts` QML (`qtchartsqml2` in `qtcharts`)
6. `Qt5Compat.GraphicalEffects` (`qtgraphicaleffectsplugin` / `qtgraphicaleffectsprivate` in `qt5compat`)

Exposing those QML plugins in `@qtdeclarative`, `@qtcharts`, and `@qt5compat` will allow `gz-gui` to bundle all of its Material style, Dialog, and Chart QML plugins statically/hermetically without runtime QML import warnings.

### 6b. Check `QtNetwork` Feature Flags (`QNetworkDiskCache` / HTTP Attributes)
In `qtbase/6.10.2/overlay/qtbase_config.bzl`, verify that all `QT_FEATURE_networkdiskcache` and `QT_FEATURE_http` symbols/sources in `src/network/access/` are compiled and exported in `qt_internal_library(name = "network")` (needed by `tile_map` and other ROS mapping plugins).
