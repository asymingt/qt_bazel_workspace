# Qt 6 for Bazel — from source, hermetic, cross-compiled

This repository is a **staging area for a set of Bazel modules that build Qt 6
from source** with a hermetic LLVM toolchain. It holds a local Bazel registry
(`bazel_registry.json` + `modules/`) with one module per Qt submodule, the
smoke tests that exercise them, and the CI that proves they build everywhere.
The goal is to upstream these modules to the
[Bazel Central Registry](https://registry.bazel.build); until then you can use
them directly from here.

## Why build Qt from source?

The existing Bazel integrations download the official prebuilt Qt binaries.
That is convenient, but it quietly breaks the guarantees Bazel is supposed to
give you:

- **Prebuilts assume GCC and libstdc++.** The official Linux binaries are
  compiled with GCC against libstdc++. Link them from a Clang/libc++ toolchain
  (as any hermetic LLVM setup does) and you are mixing two C++ standard
  libraries and two ABIs in one process — at best a wall of warnings, at worst
  `std::string`/`std::function` layout mismatches that surface as crashes at
  runtime rather than errors at build time.
- **Prebuilts are not self-contained.** They dynamically load a long tail of
  system libraries at *runtime* — `libxcb-*`, `libxkbcommon`, `libGL`,
  `fontconfig`, `libdbus`, `libpulse`, `libgstreamer`, and so on — which must
  be installed via `apt` on every machine that builds *and* every machine that
  runs the result. Which versions you get depends on the host image, not on
  Bazel, so builds are no longer reproducible and remote execution is a
  gamble.
- **Cross-compilation is off the table.** A downloaded SDK is for one
  OS/architecture; targeting another means a different download, a different
  sysroot and, on macOS and Windows, a non-hermetic native SDK.

Building Qt — and its X11/D-Bus/multimedia dependencies — from source inside
the action graph with one hermetic Clang toolchain fixes all three: a single
ABI end to end, nothing read from `/usr` at build or run time, and
`--platforms=...` as the only difference between a Linux, macOS or Windows
binary.

## Try it now

Point Bazel (**9.0 or newer** — `rules_cc` ≥ 0.2.21, which the hermetic LLVM
toolchain depends on, needs Bazel 9's C++ runtime toolchain type) at the GitHub
Pages mirror of this registry, ahead of the BCR, in your `.bazelrc`:

```
common --registry=https://asymingt.github.io/qt_bazel_workspace/
common --registry=https://bcr.bazel.build
```

Then depend on Qt like any other module:

```starlark
# MODULE.bazel
bazel_dep(name = "llvm", version = "0.8.25")   # hermetic toolchain
bazel_dep(name = "qt", version = "6.10.2")     # rules
bazel_dep(name = "qtbase", version = "6.10.2")
bazel_dep(name = "qtdeclarative", version = "6.10.2")
register_toolchains("@llvm//toolchain:all")
```

```starlark
# BUILD.bazel
load("@qt//:qt.bzl", "qt_cc_binary")

qt_cc_binary(
    name = "app",
    srcs = ["main.cc"],
    deps = ["@qtbase//:widgets", "@qtdeclarative//:quick"],
)
```

Cross-compile the same target for any supported platform with nothing but a
flag:

```
bazel build //:app --platforms=@llvm//platforms:macos_arm64
bazel build //:app --platforms=@llvm//platforms:windows_amd64
bazel build //:app --platforms=@llvm//platforms:linux_arm64_gnu.2.34
```

### Toolchain requirements

The overlays assume Clang with libc++ on every platform (on Windows, the
`win32-clang-g++` mkspec with a MinGW sysroot); they set `-std=gnu++20`
themselves. MSVC (`cl.exe`/`clang-cl`) is not supported; so far only the `qt`
module's `win_cxxabi_shim` is marked incompatible with it via
`@rules_cc//cc/compiler`. This workspace's `.bazelrc` also sets flags the
build currently relies on: `--features=system_include_paths`,
`--@llvm//config:experimental_stub_libgcc_s=False`, and a per-file
`-Wno-thread-safety-analysis` for Qt sources. We recommend registering the
hermetic `@llvm` toolchain as shown above.

## How this differs from other Bazel + Qt projects

The user-facing API (`qt_cc_library`, `qt_cc_binary`, `qt_ui_library`,
`qt_resource`, `qt_qml_module`, `qt_plugin`) is deliberately modelled on
[Vertexwahn/rules_qt6](https://github.com/Vertexwahn/rules_qt6) and its
ancestors ([justbuchanan/bazel_rules_qt](https://github.com/justbuchanan/bazel_rules_qt),
[bbreslauer/qt-bazel-example](https://github.com/bbreslauer/qt-bazel-example)),
so existing projects can switch by changing a `load()` path. Under the hood it
is a different thing:

- **Qt is built, not downloaded.** Nearly every existing project
  (`rules_qt6`, `aabtop/rules_qt`, `jheaff1/rules_qt`, ...) wraps a prebuilt or
  system Qt. Here every Qt library, plugin and code generator (`moc`, `rcc`,
  `uic`, `qsb`, `qmltyperegistrar`, ...) is compiled in the Bazel action graph
  from hash-pinned upstream source tarballs. No SDK download, no system Qt.
- **Hermetic and cross-compilable by construction.** Builds use the
  [hermetic LLVM toolchain](https://github.com/hermeticbuild/hermetic-llvm):
  no Xcode, Visual Studio or Windows SDK. One Linux host can produce
  Linux/macOS/Windows binaries for x86_64 and arm64, including the native
  `xcb`/`wayland`, `cocoa` and `windows` QPA plugins.
- **One bzlmod module per Qt submodule.** Unlike monolithic from-source
  efforts ([kklochkov/rules_qt](https://github.com/kklochkov/rules_qt),
  [OpenROAD/qt_bazel_prebuilts](https://github.com/The-OpenROAD-Project/qt_bazel_prebuilts)),
  Qt is split along its own submodule boundaries with the Starlark factored
  into a shared `qt` module, so modules version and depend on each other
  through a registry exactly like any other BCR dependency.
- **(Almost) no patches to Qt.** Every module is the pristine upstream tarball
  plus a registry overlay (`BUILD.bazel`, `MODULE.bazel`, a config `.bzl`).
  Adding a Qt submodule means writing a `BUILD.bazel`, not forking Qt. The one
  exception is a single-line fix to `qtopcua` (see
  [Patches to Qt modules](#patches-to-qt-modules)).

## Layout

| Path | Purpose |
| --- | --- |
| `bazel_registry.json`, `modules/` | The Bazel registry, published to GitHub Pages on every merge (`.github/workflows/ci.yaml`). |
| `qt.txt` | Target pattern list (`//...` plus `@<module>//...` for all 49 registry modules), selected by `--config=qt`. |
| `tests/` | Smoke and runtime tests per Qt area (`phase4_*`, `phase5`, ...), run natively and cross-compiled by the CI matrix. |
| `design/` | Design notes and plans per phase (`PHASE1.md` ... `PHASE5.md`). |
| `patches/` | Patches for third-party BCR modules, one directory per module, applied via `single_version_override`. See below. |
| `.github/workflows/` | CI: `pull_request.yaml` (build/test matrix), `bazel.yaml` (one host/target job), `cache_cleanup.yaml`, `ci.yaml` (registry publishing). See [Continuous integration](#continuous-integration). |
| `.bazelrc` | Toolchain flags, `--config=qt`, and sanitizer configs. No platform is pinned, so `bazel test //...` builds natively on any supported host; cross-compile by passing `--platforms=@llvm//platforms:<os>_<arch>` explicitly. Warnings from third-party (non-Qt) dependencies are silenced so that Qt's own stand out. |
| `bazel_downloader.cfg` | Download mirrors for upstream tarballs of BCR modules we cannot annotate with `mirror_urls` (currently `fontconfig`). |

## Continuous integration

`pull_request.yaml` runs on every pull request and on every push to `main`:

1. **Native** (6 jobs): build `--config=qt` (`//...` and every `@<module>//...`) and test `//...` on each of Linux, macOS and Windows, x86_64 and arm64.
2. **Cross** (30 jobs): every host cross-compiles `--config=qt` for every other platform. These only start once all native jobs are green.
3. **`last_rc`**: repeats the native and cross matrix with Bazel's latest release candidate. Its failures are reported but never fail the run.
4. **Status** (`main` only): publishes one [build status](#build-status) matrix per Bazel version to the `status` branch.

Each job keeps a Bazel disk cache in GitHub's Actions cache, keyed by host,
target and commit and pruned to what the build used. GitHub lets every pull
request restore caches saved on `main`, but never another pull request's, so
`main` seeds the shared caches (runs on `main` are never cancelled by a later
merge, and only the 9.x stage saves). A pull request saves its own
caches for quick re-runs, and `cache_cleanup.yaml` deletes them once it is
merged or closed.

## Patches to Qt modules

One Qt module carries a registry patch (`modules/<module>/<version>/patches/`),
applied for every consumer of the published registry:

| Module | Patch | Why |
| --- | --- | --- |
| `qtopcua` | `provider_plugin_ownership.patch` | `QOpcUaProvider`'s destructor deletes backend plugin instances that are owned by its `QFactoryLoader`. With statically linked plugins (as here) the loader deletes them again at process exit, through an already-destroyed `static QPointer`, which crashed `opcua_qml_test` intermittently. The patch leaves deletion to the loader. |

## Patches to third-party modules

A few *third-party* Bazel modules are patched via
`single_version_override` in `MODULE.bazel`, with the patch files kept under
`patches/<module>/`. These only apply inside this workspace (overrides are not
part of the published registry); each one is a stopgap we intend to drop once
the fix lands upstream.

| Module | Patch | Why |
| --- | --- | --- |
| `llvm` | `patches/llvm/*.patch` | Toolchain fixes for the hermetic LLVM module: header search paths, sanitizer runtimes, Windows `@params` files, de-duplicated `-rpath` entries, quiet MinGW `.def` preprocessing, and extracting the `System/Cryptexes` targets of macOS SDK frameworks (WebKit, JavaScriptCore). |
| `ffmpeg` | `patches/ffmpeg/sysctl.patch` | Make the `HAVE_SYSCTL` configure check a link test (`AC_TRY_LINK`) so it is answered correctly when cross-compiling. |
| `openssl` | `patches/openssl/windows_clang.patch`, `perlasm_gnu_section_syntax.patch` | Select the right generated `configdata.pm`/build config for Windows when compiling with clang + MinGW rather than MSVC; always emit the GNU `.section` syntax that clang accepts (the assembler probe does not work under `cmd.exe`). |
| `libjpeg_turbo` | `patches/libjpeg_turbo/mingw_copts.patch` | Select MSVC-only copts by compiler rather than by OS, for MinGW targets. |
| `rules_perl` | `patches/rules_perl/windows_arm64_emulated_x86_64.patch` | See below. |

### `rules_perl`: Perl on Windows/ARM64 hosts

The BCR `openssl` module runs Perl at build time (header templates, perlasm,
`buildinf.h`), so it needs a Perl toolchain on the **execution** platform.
`rules_perl` has no toolchain for Windows/ARM64 because
[Strawberry Perl does not publish an arm64 build](https://github.com/StrawberryPerl/Perl-Dist-Strawberry/issues/218)
([bazel-contrib/rules_perl#116](https://github.com/bazel-contrib/rules_perl/issues/116)).
As a result, *building on* a Windows/ARM64 machine fails toolchain resolution
for `@openssl//:progs_gen` — even though *targeting* `windows_arm64` from any
other host works fine, since the Perl steps run on the host.

We carry the change from
[bazel-contrib/rules_perl#125](https://github.com/bazel-contrib/rules_perl/pull/125)
(rebased onto the released `rules_perl` 1.1.2): it registers a `windows`/`arm64`
toolchain that reuses the hash-pinned x86_64 Strawberry Perl archive and relies
on Windows-on-Arm's built-in x64 emulation to run it. Perl is a plain
interpreter with no CPU-specific code generation, so this is correct, just
slower. It requires Windows 11 on Arm (Windows 10 on Arm only emulates 32-bit
x86) with the "Turn off x64 emulation on Arm" policy unset — both true of
GitHub's `windows-11-arm` runners.

Remove the patch and the `rules_perl` override in `MODULE.bazel` once a
`rules_perl` release includes #125 (or a native arm64 Perl).
